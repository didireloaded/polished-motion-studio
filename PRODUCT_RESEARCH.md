# NamLink feature audit and product research

Research checked 29 October 2026. This document distinguishes a screen or local interaction from a production, multi-user feature.

## What is in the shared Lovable project today

Lovable project `Polished Motion Studio` (`01804eef-1c82-496a-b1ef-dacee9edd43c`) is saved through commit `b3cd8c9`, the same commit pushed by Codex. Its database is **not enabled**. The current app is a TanStack Start client-side preview whose activity state is stored in browser localStorage. There are no server routes, authentication, remotely shared activity, or backend data models in this repository.

## Codex and Lovable parity

The local Codex repository and Lovable have the same app source at `b3cd8c9`; Codex’s latest UI/state pass is present in Lovable. The five tabs are Home, Nearby, Posts, Chats and You. The preview includes the Discover photo card, animated in-card details reveal, filters, explicit like/pass/save actions, local sample match, Nearby town list, local event-interest toggle, named-author/private-reply interface with 300-character caps, match-only Chats list, profile editing, This-or-that choices, local voice recording, and an explicitly unverified selfie preview.

The distinction is hosting and truthfulness, not two different feature sets: both versions currently use the same front-end prototype code and localStorage, and Lovable’s PostgreSQL database is disabled. A feature being clickable in both places does not mean accounts can exchange it.

## How established dating apps operate

### Discovery and recommendations

1. **Eligibility first:** honor each person’s age, gender/relationship preferences, location/distance, account visibility, blocks, prior decisions, and safety status. Tinder’s public description starts with location, gender, age and distance preferences.
2. **Candidate retrieval:** find a manageable set of eligible profiles near the chosen location or within the permitted market. Production systems use indexed geographic and profile retrieval rather than loading every profile into a client.
3. **Ranking:** estimate reciprocal fit, not just whether the current user might like the candidate. Use declared intent and preferences plus profile completion, shared interests/prompts, and consented behavioral signals. Bumble describes recommendations using profile and past-match signals; Tinder describes engagement and profile signals and says it no longer uses Elo.
4. **Reranking:** balance compatibility, freshness, exposure and diversity. Do not turn popularity into a feedback loop that repeatedly hides less-exposed members. The research literature identifies exposure concentration as a real two-sided-market failure mode.
5. **Learn conservatively:** skips/likes and completed conversations may improve suggestions, but avoid sensitive-trait inference and offer a clear reset. New accounts need a fair cold-start path.

The private scoring formula used by Tinder/Bumble is not public. The design above is an evidence-based product recommendation, not a claim to reproduce their proprietary algorithm.

### Likes and matches

- A like is a private expression of interest, not a public post or chat.
- Create a match only when both active accounts have liked one another and still meet visibility/block rules.
- Make matches idempotent and transactional; prevent duplicate likes/matches and serialize simultaneous reciprocal likes.
- A pass should remove the person from the current queue; undo, if supported, should be bounded and auditable.
- Avoid paid visibility or “who liked you” gates for NamLink’s no-paywall launch.

### Chats

- Only a mutual match (or the explicitly designed post-reply connection path) grants a conversation.
- Persist messages server-side with participant authorization on every read/write, pagination, delivery state, basic abuse limits, block/unmatch revocation and reporting.
- Do not permit a browser client to create a match by directly writing its own `matches` list.
- Bumble’s conversation options show opening prompts and optional voice/video are product choices layered on the same match gate; they are not necessary in the first backend slice.

### Nearby and crossed paths

- Nearby can be a map/list hybrid, but markers must be approximate, opt-in, and reveal no live coordinates or exact distance. A profile selection opens a profile/like action; a mutual like still gates chat.
- Crossed paths is a separate, opt-in feature. It needs native mobile background location, disclosure, OS authorization, sampling/geofencing, retention/deletion limits and abuse protections. The visible history should be delayed/coarse (for example, “earlier today near central Windhoek”), never pinpointed or a live “500 m away” indicator.
- Web geolocation cannot reliably deliver the requested background/DND behavior. Apple's documentation requires deliberate authorization and background configuration; Apple asks apps to explain location purpose and obtain consent. Defer background crossed-path notifications until there is a native iOS app and a reviewed privacy design.
- Do not expose another member’s exact crossing point. Happn’s published trust charter says crossing locations are deliberately imprecise; academic security work documents how granular location in dating apps can expose people to stalking.

### Events and posts

- **Events:** an event has an owner, verified/validated details, attendees/interest visibility, privacy settings, capacity/state and reporting. Show “interested” members only under an explicit visibility choice. Do not notify a person that another member is interested. A mutual “both interested” confirmation may create a planning connection; it must not silently create a romantic match unless the user opts in.
- **Posts:** this latest product direction changes prior anonymity: show the author’s name. Keep replies visible only to the author and replier, enforce a 300-character maximum on both post and reply, and allow an author to like a reply to open a chat/connection. The database must enforce participant-only read access; hiding replies in the UI is not privacy.

## Recommended NamLink behavior

1. Keep the five-tab structure and warm, restrained iOS-style visual language. Discover remains the photo-led home; profile details now reveal beneath the image in-card. Continue applying native-feeling, borderless pickers/selectors consistently.
2. Keep likes private and chat behind reciprocal consent. Replace `mutualInterest` sample logic with server-side matching.
3. Build Nearby as a map/list hybrid with coarse, opt-in presence; make Crossed paths its own view and keep it out of continuous tracking until native iOS consent and retention controls are designed.
4. Rename the Nearby section “Events.” (The event subsection is now labeled Events.) Give event attendance explicit visibility choices and require a mutual opt-in before offering to plan together.
5. Posts now use named authors and a 300-character cap in the local preview, with private author/replier UI. Implement server-side participant authorization and remove aggregate reply counts if they could reveal engagement.
6. Keep Chats compact and snappy; add message/report/block/unmatch paths before opening a real beta.
7. Build authentication and authorization before implementing multi-user likes, chats, posts or events. The current code cannot safely become a production service by adding UI-only state.

## Suggested implementation order

1. Product screen pass: profile reveal animation, refined Nearby map/list and dedicated Crossed paths view, Events wording/visibility, named posts/300-character counters, consistent iOS selectors. Use clearly labeled demo data until a backend exists.
2. Trust foundation and backend: adult onboarding/age policy, auth, profile/photo storage, blocking/reporting/moderation, server-side likes/matches, RLS/access control.
3. End-to-end core beta: shared likes and mutual matches, authorized chats, real named posts with private replies, event records and opt-in attendance.
4. Native features: verification provider and native iOS location/crossed-path notifications only after consent, precision, retention, deletion, abuse and App Store requirements are settled.
5. Recommendation iteration: start rule-based and explainable; measure eligible coverage, reciprocal-like rate, first-message rate and safety outcomes, then tune with privacy-reviewed data and exposure caps.
